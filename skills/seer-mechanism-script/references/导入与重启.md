# 导入与重启

## 脚本与参数文件

仙工《机构脚本使用通识介绍》修订 826，第 2–5 节：控制器的 `syspy` 是系统目录；把自定义脚本及依赖放在客户脚本路径。修改被引用的模块文件后，厂商要求重启控制器。第三方库需按目标环境确认源码、依赖和路径；本地能安装不代表控制器有对应包。

SDK 示例同时有顶层导入（`from rbk import ...`）和带包名导入（`from syspy.rbk import ...`）。包内 `rbk.py` 自身有 `from rbkSim import SimModule`，`robot.py` 还引用 `requests` 和顶层 `goPath`；因此要核对入口及传递依赖。拆文件前确定依赖放置、加载方式及回退文件集合。

本地 `ParamServer(__file__)` 按传入文件名生成同目录 `params/<脚本名>.json`（实现取首个点前的文件名）。通识第 4.1.1 节有一处写成 `param`；第 2.1 节及压缩包源码均为 `params`。检查模块顶层和类体：若在这些位置调用 `ParamServer`，导入就可能写配置。改名或移动调用时，确认传入的文件路径是否改变。用临时副本做导入检查。若 RoboShop 无法生成参数面板，按通识第 4.2.1 节核对相对导入和 `__main__` 中的 `Module` 实例化；生成参数无需调用 `run`。

## 检查本地能否导入 syspy.rbkSim

先确认回放实际使用的解释器和工作目录。用同一个解释器，从该目录运行下方命令。确认 SDK 来源后，只导入 SDK 模块。探针所查的导入应和待维护脚本一致。以下示例适用于同时使用 `syspy.rbkSim` 和 `syspy.rbk` 的脚本。

```sh
python3 -B - <<'PY'
import sys
from pathlib import Path

print(f"Python: {sys.executable} ({sys.version.split()[0]})", flush=True)
print(f"工作目录: {Path.cwd()}", flush=True)
from syspy.rbkSim import SimModule
from syspy.rbk import BasicModule, MoveStatus

for name in ("syspy.rbkSim", "syspy.rbk", "rbkSim"):
    module = sys.modules.get(name)
    if module is not None:
        print(f"{name}: {module.__file__}")
PY
```

- 缺少 `syspy` 或 `syspy.rbkSim` 时，检查是否已有与目标控制器匹配的 SDK。若只有厂商 ZIP，把源码解到临时目录的 `syspy/` 下，让包含 `syspy/` 的上一级目录进入本次进程的 Python 搜索路径，再跑探针。核对 `rbkSim.py` 的大小写和解压后的目录层级。
- `syspy.rbkSim` 能导入，但 `syspy.rbk` 报缺少顶层的 `rbkSim` 时，先检查该版 `rbk.py` 是否用了 `from rbkSim import SimModule`。若是，将 `syspy/` 本身也加入本次进程的搜索路径。例如本地 Linux 或 macOS 回放时，在探针命令前加 `PYTHONPATH="/path/to/replay:/path/to/replay/syspy"`，并换成实际路径。若缺少其他模块，按 traceback 核对实际缺失的传递依赖。
- 导入成功后，比对打印的路径和预期 SDK 的位置。若加载了其他目录的同名模块，检查搜索路径和顺序。记录所用解释器、实际模块路径，或首个缺失的模块。这个结果只覆盖本地环境。控制器端以实际加载记录为准。

## RoboShop 与生效检查

1. 做发布清单：控制器版本、入口、依赖、原脚本与现用 JSON、模型文件、调用方任务和回退版本。先区分控制器与本地哪份较新；必要时拉取控制器文件以便比对。
2. 在「机构脚本」客户文件列表导入自定义文件，并检查本地与控制器的差异标记。导入、推送、运行是不同操作；「推送并运行」会覆盖控制器文件并执行脚本。
3. 调配置时保留原参数文件，改对应 `value` 并推送。变更依赖模块后按厂商要求安排重启；参数已推送仍不生效时，先核对路径、覆盖来源和版本，通识第 2.1 节建议重启。部署方案写清何时重启、如何回读及如何回退；本地维护不执行这些现场操作。

## 调用绑定

通识第 8 节列出 RoboShop 直接运行、任务链、RDS Core Web API、SRC TCP API、RDS `bintask`、模型 `Trigger` / `PeriodRun`。普通任务链的外层字段包含 `operation`、`script_name`、`script_args`，外层动作与脚本内部 `args["operation"]` 分开核对。`PeriodRun` 调 `periodRun(r)`，不照搬普通作业入口。核对实际下发参数和控制器上的入口文件；有调度回包时，再单独追踪 RoboKit 作业状态与设备反馈。

## 核对实际运行版本和生效参数

选定同一台控制器和同一次作业，用任务标识、时间和调用入口关联记录。优先使用已有下发记录、RoboKit 日志及文件回读。

1. **入口。** 从调用方记录确认实际下发的入口和任务参数。比对控制器上对应的入口文件与待核对版本，记录版本标识或文件校验值。
2. **依赖。** 比对入口实际引用的依赖文件。若有加载记录，核对入口和模块的 `__file__`，以及实际的 RoboKit 和 Python 版本。依赖更新涉及重启时，核对重启记录和下一次作业的加载记录。文件回读能确认控制器上的文件内容，加载记录能确认作业用的是哪一份。
3. **参数。** 回读入口对应的配置 JSON，取相关字段的 `value`。对照本次实际传入的 `args` 和脚本的覆盖、归一化与派生逻辑。记录每个待查参数的来源、单位、最终值和使用位置。能从同一次作业的日志或上报读到最终值时，拿它与计算结果比对。

结论写到证据支持的阶段。只有文件回读和离线推导时，分别记录文件内容和预期参数，把实际加载的依赖和作业生效值标为待核实。需要加诊断时，在作业初始化后按需记录路径、版本与有关参数，每次作业记录一次，并排除凭据等敏感值。
